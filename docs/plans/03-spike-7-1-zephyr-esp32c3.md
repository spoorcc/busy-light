# 03 -- Spike 7.1: Zephyr on ESP32-C3 (design doc)

- **Status:** Draft (goldfish comprehension and antagonistic passes run, see RV-002; the owner has not approved it)
- **Date:** 2026-11-03  **Owner:** Ben Spoor
- **Area:** sw (exploratory; no product code)
- **Requirements addressed:** none are implemented. The spike measures the feasibility of SYS-012, SYS-026, SYS-027, SYS-029, SYS-034, SYS-036, SYS-043, SW-002 and SW-004, and answers open questions in ADR-0002, ADR-0006, ADR-0007 and ADR-0008.
- **EGM review record:** RV-002

## 1. Problem definition
Plan 02 and ADR-0002..0008 depend on facts about Zephyr on the ESP32-C3 that nobody has checked: flash fit, heap, access point with station, MCUboot together with the chip's secure boot, TLS server and client together, LED output during Wi-Fi traffic. Until these are measured, the ADRs cannot be accepted and the requirement values stay guesses (RV-001 readiness pass: NO-GO).
Out of scope: product code, the web page design, the mapping model, hardware design, any step that cannot be undone on a board that is not a sacrificial one.

## 2. Constraints and assumptions
- Process rule (`docs/process/README.md`): spike code lives only on a branch `spike/7.1-zephyr-esp32c3`, is never merged, and its results go into `docs/verification/reports/spike-7-1.md` on the normal branch. Code written here is thrown away or rewritten under Approved requirements with tests.
- A1: the ESP32-C3-DevKitM-1 (module ESP32-C3-MINI-1, 4 MB flash) is representative of the planned module *(verify the flash size of the kit at purchase)*.
- A2: Zephyr v4.2.0 as pinned in `sw/west.yml`. If a needed feature exists only in a newer release, the spike records that and tests the newer release as a second run.
- A3: free tools only, and a PC build (Wokwi excluded, owner round 7).
- A4: the owner runs the hardware steps. I (Claude) write the procedure and the scripts, and analyse the logs the owner pastes or saves. I do not claim a measurement that nobody made.
- A5: eFuse steps are done only on kits marked "sacrificial" (ADR-0007 stage 2). Kits are counted separately: [3] working kits (E1 to E10, E12, E13; never fused) and [3] sacrificial kits (E11), each irreversible sub-step on its own kit. Each kit gets a physical label and a state line in the report. A kit with any eFuse step is marked "spike key, do not ship".
- A6: the spike runs on an isolated test network (separate access point, no link to the owner's production network). The soft AP, the DNS responder and the test servers never touch a shared LAN.
- A7: **entry condition.** No parts are bought for the spike and no experiment starts before the owner approves this plan. Buying parts is the owner's decision.
- A8: a pass or fail uses the value in the current requirement when one exists. A bracketed value is a working value: the result is recorded as a measurement and the owner sets the value afterwards. The spike does not set requirement values by itself.

## 3. Alternatives considered
- **Spike on a dev kit (chosen).** Fast, cheap, same module as the target.
- **Paper study only.** Rejected: the same reviewers that found the flash gap worked from memory (RV-001).
- **Build the real board first.** Rejected: it would freeze the antenna and the LED drive before the facts are known (ADR-0003, ADR-0004).
- **Do nothing.** The design stays NO-GO.

## 4. Technical plan
The spike is a list of experiments. Each has a method, a pass rule and a result field. A failure is a useful result: it names the fallback.

### 4a. Additional rules per experiment (from review RV-002)
These rules extend the table above. Where they differ from a table cell, they apply.

| Experiment | Added rule |
|------------|-----------|
| E0 | A step-0 result of "missing" for AP, AP+STA, MCUboot or secure boot stops the purchase until the owner decides (RV-002 item 3). |
| E2 | Compute the break-even first: 2 x image / 0.75 + bootloader + swap scratch or move area + partition table + settings + secrets + web files must fit in 4 MB; the report gives the largest image that fits. State the swap mode (scratch, move or offset), whether the web files are in the image or in their own partition, and the build type (release, no debug logging, assertions off); record all `CONFIG_*`. Report absolute bytes as well as percentages. |
| E3 | Clock starts at the tap on "join" (or the QR scan). Record phone model and OS version. Cases: page over HTTP (as in ADR-0008) and a TLS page with the certificate warning; the "no Internet, stay connected?" prompt; DNS answer for any name; the typed address is the pass rule, the captive-portal sheet is a bonus. Check QR escape rules for special characters in the passphrase. |
| E4 | Also: a router on a different channel than the AP start channel (a single radio forces one channel; record what the phone on the AP sees); a wrong station password; the router disappearing and returning. One run lasts at least [1] hour; the others [10] min. Record throughput and the effect on the LED frame period. |
| E5 | "Cold" means the first handshake after reset with the key present. Measure from TCP connect to first byte and keep key generation separate. State cipher suite, key type, TLS version, `MBEDTLS_SSL_MAX_CONTENT_LEN` and whether PSA crypto or the legacy API is used. The times are observations with a working limit (A8), not pass rules. Include a run with no valid time (no SNTP) and a chain verification with hostname check. Leak rule: free heap after a warm-up of [50] requests and after [1000] requests differ by at most [256] bytes. |
| E6 | Heap metric: the configured heap size, the lowest free heap and the largest free block at that point, in bytes; state which heaps exist (system heap, mbedTLS heap, Wi-Fi and network buffers). Add SW-002's case: 10 simultaneous connection attempts with a load script on the PC, the busy answer, and the LED frame period. Add a stalled client, a client that disconnects mid-handshake, and a TCP reset. |
| E7 | The update upload to the secondary slot (flash erase and write, which can stall code and interrupts) runs during the animation on purpose. Check the frame content as well as the count. A 24 MS/s clone analyser is accepted only if its decoded bit widths are within the LED tolerance; otherwise use a second microcontroller as a decoder. Set the LED brightness limit and the supply during the test and record the supply voltage at the LEDs, so that supply droop is not blamed on software. |
| E8 | Collect the first passphrase after each of [1000] cold resets (with Wi-Fi off and on) and check repeats across resets; run `ent` or a NIST SP 800-22 subset on a raw dump of the entropy source; report which entropy source is used before the radio starts. A collision test inside one run is not a pass rule. |
| E9 | State the swap mode first (it affects E2 and E10). Report the times separately: first swap, the unconfirmed run, the watchdog reset, the revert swap. Cases: hang before confirm; the web server does not start; no Wi-Fi coverage (must confirm); crash at boot loop; confirm then crash. |
| E10 | Log a flash-operation counter or a GPIO trace at each cut so that every cut is mapped to a phase. Use an electronic switch with a controlled ramp down and also a slow ramp, because hold-up capacitance makes brown-out, not a clean cut. Add the deterministic variant (a build that halts after N flash writes, and flash write failures injected in `native_sim`, as ADR-0007 plans). State the confidence: 0 failures in 100 cuts shows only about 97 % confidence that the failure rate is below 3 %. Define "invalid settings": a bad checksum is detected, and the unit falls back to defaults and never uses a partly written secret. |
| E11 | Split into E11a (no eFuse: a build of MCUboot for `esp32c3` with the chip's secure boot and encryption settings enabled in simulation or in development mode only, and a paper check of the key schemes: ROM stage versus MCUboot stage), E11b (flash encryption in reversible development mode, encrypted update, encrypted in-place first-boot encryption with a power cut) and E11c (release-mode eFuses on a sacrificial kit). E11a runs before E9 is finalised, because its outcome (MCUboot or the Espressif bootloader) decides E9. Negative tests for E11c: a wrong-key image at the ROM stage and at the MCUboot stage; `esptool read_flash` fails; UART download mode and USB-Serial-JTAG are disabled as required by SYS-043; `espefuse summary` dump after every step. The recovery path (SYS-046) is a design question first: E11c may only observe what the locked kit allows. The result does not close SYS-043 or TC-043. |
| E12 | Check first, in E0, that the Zephyr Wi-Fi driver for ESP32 exposes WPA2-Enterprise at all. Decision rule: feasible if the free flash after the SYS-026 margin is at least the added size, including room for a client certificate and key (SYS-036). Run after the final E2b build. |
| E13 | The code is a throw-away re-implementation of the SW-001 limits (the extractor does not exist yet). Measure with the cycle counter, with Wi-Fi active and idle. |
| New E14 | Power budget: peak and average current at full-white LEDs at the limited maximum plus Wi-Fi transmit, with the USB power meter and a scope or meter on the 3.3 V rail. Feeds HW-004 and spike 7.5. If the owner drops E14, the power meter leaves the shopping list. |
| All | Repeat each timing measurement [10] times and report minimum, median and maximum. Load and power-cut tests run on two boards. A result that fails in some runs is "intermittent" and counts as failed until the cause is known. Record channel, RSSI, access point model, chip revision (`esptool chip_id`), flash chip ID and the eFuse dump for every kit. Experiments that can run unattended: E4, E6, E7 soak, E10 with a script. |
| Scope if time is short | First group by value for the ADR decisions: E0, E1, E2a, E3, E11a, E9. The rest follow. The estimate of owner time is a guess: [3] to [5] days does not cover all of E0 to E14; the plan gives no better figure until E0 is done. |

## 5. Detailed implementation plan
- **Files to create (all on the branch `spike/7.1-zephyr-esp32c3`, never merged):** `sw/spike/` with one folder per experiment (`e01_hello`, `e02_budget`, ...), each with a `README.md` giving the exact `west build` line, the Kconfig used, and what to look for; `sw/spike/results/` for raw logs.
- **Files to create on the normal branch after the run:** `docs/verification/reports/spike-7-1.md` with the filled-in table, the commit hash of the spike branch, the Zephyr revision and the board; updates to ADR-0002, 0006, 0007, 0008 (Proposed, so editable) and to the bracketed values in the requirements.
- **Kconfig and devicetree:** unknown until E1. The spike records the final `prj.conf`, overlay files and board name in the report. Names I expect to need are `CONFIG_WIFI`, the ESP32 Wi-Fi driver options, `CONFIG_NET_*` sockets, `CONFIG_HTTP_SERVER`, `CONFIG_MBEDTLS_*` or the PSA crypto options, `CONFIG_BOOTLOADER_MCUBOOT`, `CONFIG_LED_STRIP` *(all to verify against the pinned release; no names are fixed here)*.
- **Groups and decision points.** Step 0: E0 (desk survey, before any purchase). Group 1 (cheap, likely to pass): E1, E2a, E3, E4, E8, E5, E6, E7, E13. Group 2 (risky): E11a, E9, E10, E2b, E12, E14, E11b, E11c. Decision point 1 after E1: if the board, Wi-Fi or `led_strip` does not work on the pinned release, the owner decides whether to test a newer Zephyr release (A2) or stop. Decision point 2 after E9: if MCUboot does not work, the owner decides on the Espressif bootloader. Time box for the whole spike: [6] weeks; per feature [2] weeks. Parts budget: [EUR 300] (a guess, to be replaced by the real prices). E11b and E11c are last because they use sacrificial kits and may destroy them; E11a is early because it decides E9.
- **Log header (script-made, in every log):** git hash of the spike branch, west manifest hash, Zephyr revision, toolchain version, board, kit label, date, and for each capture the SHA-256 of the file. Each row of the report is marked "measured", "estimated" or "not run".
- **Secrets and data handling.** Spike keys (image signing, secure-boot, flash-encryption) are generated outside the repository, labelled "SPIKE-ONLY", ignored by Git, and never used for a release. Logs are scrubbed of Wi-Fi credentials, tokens and generated passphrases before they go into Git or the report. The spike branch is not pushed to a shared remote unless it is scrubbed. The E8 passphrase list is deleted after the repeat check.
- **Result row (report template):** experiment, answers (IDs: ADR open point, SYS/SW value), result and unit, kit label, fallback taken, evidence file and hash, phone models and OS versions (E3).
- **Shopping list for the owner (after approval, A7):** [6] ESP32-C3-DevKitM-1 kits (3 working, 3 sacrificial); a 16-LED ring or strip of the chosen type; a 5 V supply and a USB power meter; a logic analyser with at least 8 MS/s; a USB relay or controllable USB hub for the power cuts; one iPhone and one Android phone; a Python test HTTPS server on the PC (a Jenkins instance only for the E5b request-step test); a separate Wi-Fi access point with WPA2 for testing (A6).
- **Rules during the spike:** every measured number is copied with its unit and the exact build; a failed experiment is reported as failed. Any local patch to Zephyr or a module gets a `DEV-` record with a plan to upstream it (round 7 decision). A feature that takes more than [2] weeks stops and goes to the owner.

## 7. Risks and open questions
- The dev kit may differ from the planned module (flash size, antenna type, USB bridge). Record the exact kit.
- The development kit's USB-serial bridge is not the same as the chip's native USB used on the final board *(verify)*. Programming and recovery tests on the kit may not transfer.
- E11 may brick the kit: that is accepted. RISK-022 is about this.
- The owner's time: E3 and E10 need phones and a rig. A rough effort estimate is [3] to [5] working days of owner time plus waiting for parts. This is a guess.
- The cost and time figures are guesses. The owner decides on the parts after approving the plan (A7).
- Regulatory: the spike has no conformity outcome. The spike runs on an isolated network (A6); the report lists the Zephyr and module revisions and licences for the SBOM (SYS-044). No CHANGELOG entry is needed for the spike itself, because it changes no product behaviour; the report and ADR updates get one when they are written.
- Traceability: ADR item numbers can drift while the ADRs are Proposed, so this plan names decisions, not item numbers. Run `python3 -I scripts/check_traceability.py` after the report is written.
