# ADR-0022: Automated compliance checks in CI (design rules for EMC, substances, identification and CRA)

- **Status:** Proposed (written by the assistant, 2026-11-10; the owner decides)
- **Date:** 2026-11-10
- **Deciders / reviewers:** Ben Spoor (owner); no goldfish review run yet
- **Related:** HW-018, HW-019, HW-020, SW-011, SW-012, SYS-044, SYS-048, SYS-049, ADR-0001, ADR-0012, DEV-007, `docs/regulatory/automated-checks.md`

## Context and problem
The owner asked for as many DRC, ERC and CI static-analysis checks as possible that support the applicable EU rules (RED, CRA, RoHS, REACH, WEEE, GPSR). KiCad's ERC and DRC already run strictly (`scripts/ci_hw.sh`, ADR-0012). They check electrical and geometric rules, but not the design rules that market-access evidence depends on: a clamp on every interface net, test access, board identification, part numbers and material declarations, lifecycle. On the software side `sw/.clang-tidy` existed but did not run in CI, there was no MISRA tool run (ADR-0001 left the tool open), no SBOM step, no check of the Kconfig attack surface, no secret scan and no check of the CI supply chain.

Not known: whether the owner wants advisory MISRA rules enforced; whether a commercial MISRA checker will be bought for a compliance report; the exact harmonised standards (the official lists could not be opened, `standards-list.md`).

## Alternatives considered
### A. Project rule scripts on the KiCad text files plus open-source analysers in CI (gate/report split, waivers tied to DEV records)
A read-only s-expression parser (`scripts/kicad_sexp.py`) and rule scripts (`check_hw_compliance.py` HWC-001 to HWC-009) read the stored board and schematic; a materials register holds RoHS, REACH and lifecycle data per MPN. Software: clang-tidy (CERT C), cppcheck with its MISRA addon, a Kconfig policy, a secret scan, a CI supply-chain check and `west spdx`. Each rule is `gate` (fails CI) or `report` (evidence only); a waiver needs a DEV, RISK or ADR record and a stale waiver fails. A catalogue (`automated-checks.md`) and DOC-001 keep the documents and the code in step. Pros: no licence cost, full control, net-level rules are easy, runs in seconds, findings link to legal references. Cons: the project maintains the rules; the parser covers only what the rules need; cppcheck cannot preprocess Zephyr headers (files that need Zephyr get clang-tidy only); no MISRA compliance claim is possible from cppcheck.
### B. KiCad-native rules only (custom `.kicad_dru` DRC rules, ERC settings, kicad-cli)
Pros: one tool, rules visible in the KiCad GUI. Cons: the DRC rule language works on geometry and net classes; it cannot express "every net of J1 reaches a clamp" or read part numbers against a materials register; the `.kicad_dru` file must be generated by script (CLAUDE.md rule 12); software checks are not covered.
### C. Commercial tools: a qualified MISRA checker (for example PC-lint Plus, Helix QAC or Polyspace) and a component-compliance database service
Pros: a MISRA compliance report with tool coverage statements; vendor-maintained RoHS/REACH and lifecycle data. Cons: licence cost per seat and per year, not usable by open-source contributors, still no net-level hardware rules; the substance data still needs manufacturer declarations for the technical file.
### D. Do nothing now; check at the release gate by review and at the test lab
Pros: no work now. Cons: gaps found late (a missing CC clamp after the board is made), no recorded evidence trail, against the process (specification and evidence first).

## Comparison
| Criterion | A | B | C | D |

| Readable evidence with legal basis | yes (JSON + catalogue) | DRC report, no legal link | yes for MISRA | review notes only |
| No false pass | yes (NOT RUN printed, stale waivers fail) | yes | yes | no |

| Runs without KiCad | yes | no | yes | -- |
| MISRA claim strength | weak (no claim) | -- | strong | -- |

## Decision
Recommendation: **A**, with C kept open for the MISRA compliance report before release if the owner wants a MISRA claim. A is the only option that checks the net-level and part-level rules at all, it costs no licences, and it fails loudly when it cannot run. The policy choices inside A, for the owner to accept or change:
1. MISRA Mandatory and Required findings fail CI; Advisory findings are reported (the gate firmware has 14 Advisory findings, rules 15.5, 17.8, 8.7). A rule missing from the category table is treated as Required.
2. SWC-002 (hardening options) and HWC-007 (material declarations) stay `report` until a product configuration and a product board exist; then they become `gate` by an update of this ADR.
3. The spike board's gate findings are waived under DEV-007 (Proposed).

## Consequences
- Positive: the CC-line ESD gap, the missing board identification, three part numbers lost in the stored schematic and the NRND part were found on the first run; the SBOM is produced in CI; the compliance matrix cannot drift from the requirements.
- **Negative / trade-offs accepted:** rule maintenance by the project; the HWC rules check what the configuration says (which parts are interfaces and clamps), so a wrong configuration hides a gap; cppcheck MISRA coverage excludes Zephyr-dependent files; no MISRA compliance claim.
- New risks: a reviewer may read a green CI as "compliant". Mitigation: each script and the catalogue state what the checks do not show (`automated-checks.md` section 3).
- Requirements created: SYS-048, SYS-049, HW-018, HW-019, HW-020, SW-011, SW-012 (all Draft).

## Verification and revisit
Each script has pytest tests, including the stored spike board and a probe with known violations (clang-tidy CERT ERR34-C and four Required MISRA rules found on 2026-11-10, then the probe was deleted). Revisit when: the product board is generated (turn the report rules into gates), a MISRA claim is needed (option C), cppcheck gains Zephyr support or another open-source MISRA tool is chosen, or the official standards lists are checked and change a basis.

## Critical review notes
Strongest objection: "Home-made rule scripts are not a qualified tool; the evidence is weak." Answer: the scripts check design rules, not conformity; their output is evidence that a stated rule holds, with tests that show each rule fires. The conformity evidence remains the lab reports and the declarations. The second objection: "Waivers make red builds green." Answer: each waiver needs a DEV record that the owner approves, and a waiver that matches no finding fails, so fixed items must be removed.
